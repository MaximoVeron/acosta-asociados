## Specs

- S1: ES Modules en todo el proyecto (`"type": "module"`), extensión `.js` en imports locales.
- S2: Stack obligatorio: express, pg, sequelize, dotenv, cors, bcrypt, jsonwebtoken, cookie-parser, express-validator (ya instalados con pnpm en `api-rest/`).
- S3: Arquitectura en capas `src/{config,models,middlewares,validators,services,controllers,routes,clients}` + `src/app.js` + `server.js` raíz. (El proyecto existente se llama `api-rest/`, se respeta ese nombre.)
- S4: Modelo User: id UUID PK, name, email único, password hasheado (bcrypt), role ENUM 'ADMIN','LAWYER','ASSISTANT', licenseNumber nullable, isActive default true.
- S5: Modelo Party: id UUID PK, legalName, taxId único, entityType ENUM 'INDIVIDUAL','COMPANY', address, email, phone, representative, isActive. No inicia sesión.
- S6: Modelo Contract: id UUID PK, title, type, status ENUM 'DRAFT','UNDER_REVIEW','APPROVED','CANCELLED', extractedData JSONB, content TEXT. FKs: contractorId y contracteeId (Party), createdById (User), approvedById (User, nullable).
- S7: RBAC: solo LAWYER y ADMIN pueden aprobar contratos (RF07) — `PATCH /:id/approve` con middleware `authorizeRoles('LAWYER','ADMIN')`, setea status 'APPROVED' y approvedById = req.user.id. ASSISTANT nunca aprueba.
- S8: Seeder automático al iniciar (findOrCreate, no duplica): usuarios "admin@gmail.com"/"123" "Administrador Sistema" ADMIN; "abogado@gmail.com"/"123" "Dra. Valeria Acosta" LAWYER licenseNumber "T.º 12 F.º 345"; "asistente@gmail.com"/"123" "Marcos Asistente" ASSISTANT. Partes: "Distribuidora del Litoral S.R.L." taxId "30-71234567-8" COMPANY "Av. San Martín 1250, Rosario, Santa Fe" representative "Marcos Ezequiel Ibarra, DNI 28.456.789, socio gerente"; "Lucía Belén Fernández" taxId "35.678.901" INDIVIDUAL "Calle Mitre 845, 3.º B, Rosario, Santa Fe"; "Transportes Río Paraná S.A." taxId "30-70987654-3" COMPANY "Ruta Nacional 11 km 12, Santa Fe" representative "Sr. Julián Montiel (Apoderado)". Contrato ejemplo "Contrato de Prestación de Servicios Profesionales" entre Distribuidora del Litoral (contratante) y Lucía Belén Fernández (prestadora), creado por el asistente, status UNDER_REVIEW. Las validaciones deben permitir contraseñas cortas como "123" en desarrollo.
- S9: Auth: POST /register (bcrypt), POST /login (JWT en cookie HttpOnly `token`, sameSite 'strict', secure según entorno; devuelve usuario sin password), POST /logout (res.clearCookie('token')), GET /me (verifyToken).
- S10: Endpoints bajo /api/v1: users (CRUD; solo ADMIN crea/edita roles/desactiva; LAWYER y ASSISTANT listan personal activo), parties (CRUD + ?search= por Razón Social o CUIT/DNI, usuarios autenticados), contracts (POST crea DRAFT con createdById=req.user.id; GET y GET /:id incluyen Party y User creador/aprobador; PUT /:id; PATCH /:id/approve).
- S11: Middleware reutilizable validateRequest (express-validator) antes de controladores; errorHandler centralizado; CORS con credentials: true.
- S12: Stub `clients/agentClient.js` preparado para el futuro microservicio Python.
